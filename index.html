Progressive Loading

为什么技能要分四层

把全部工具塞进上下文，等于每轮都在为用不到的能力付 token。分层加载让 Agent 只在需要时展开细节。

层级内容加载时机与代价
L0常驻 系统工具 · FC schema 始终在上下文里。数量受控，只放真正高频的：文件、Shell、检索、计划、画布。
L1索引 <agent-skills> 技能目录 只有名字加一行用途。几十个字撑起整个能力地图，Agent 靠它判断该往哪层走。
L2入口 skill_find read → SKILL.md 命中意图才读入口文档。包含硬规则、陷阱清单与脚本资产表，是"先读文档再动手"的落点。
L3展开 load 参考 + activate 工具组 真正解锁业务工具与深度参考。不可逆操作前强制加载，避免在未激活工具上硬撞。
Harness

横切运行时：让 Agent 不跑偏

Harness 以中间件形式接入，不侵入业务逻辑。它管三件事：说清楚、别撞墙、装得下。

Prompt Cache

为缓存命中而设计的提示词布局

大模型厂商按前缀命中缓存计费与加速。若系统提示每轮都在变，前缀就得整段重建 —— 所以 Harness 把提示块按变动频率分成三类，只让该变的变。

Prompt 块分类 · 前缀从稳到动
stable 跨会话恒定，构成可缓存前缀 soul.mindset · harness.tool_discipline · harness.runtime · skills.loaded · capabilities.loaded 永不改字节
turnFrozen 回合内冻结，中途重放同一份快照 session.env 时钟、规划器闪烁都不会重写前缀；新出现的 hint / memory / 清单只允许追加一次 turn_open 快照
hopDynamic 每跳可变，排在末尾 session.file_working_set · task.workflow_draft.progress —— 变动只影响后缀，前缀照常命中 尾部可丢弃

为什么要这么排

场景切换（chat ↔ execute）会让目录块增减。若把它们放进稳定前缀，每次切换都触发整段重建。

未分类排列 · 会话均值0%
三类分块 · 稳态单次0%
数据来自源码注释记录的实测：把易变块移出稳定前缀后，稳态单次命中率可达 89%+， 而混排时会话均值被拉低到 50% 附近。工具表面预算（tool surface budget）同理 —— 宁可裁剪，不整块删。
Anthropic

explicit markers

显式 cache_control 标记缓存断点，稳定块进标记系统消息，一次性 hint 拖到真实消息之后。

DeepSeek

append-only units

只认完整单元追加。冻结块必须留在系统单元内，中途丢弃会导致「A+B 然后 A+C」双双失效。

百炼 / OpenAI 系

implicit prefix

按消息前缀隐式命中。仅极小白名单进标记消息，其余按稳定序排列，避免字典变更插在两个稳定块之间。

Model Layer

云端随意换，本地也能跑

模型是可插拔配置，不是硬编码依赖。三类槽位各管一职，失败自动降级； 想完全离线，接本地推理服务即可，无需 API Key。

本地模型 · 零 Key

ollama · llama_cpp · openai_compat

内置无 Key 通道：识别到本地服务时跳过凭证校验，直接探活注册。 Ollama 默认指向 127.0.0.1:11434，llama.cpp 与任意 OpenAI 兼容端点填个 base_url 就能接。

Ollama llama.cpp / GGUF OpenAI 兼容端点 OpenRouter keyless 探活

自定义模型面板支持增删改；model_catalog 技能可让 AI 自己完成注册与连通性验证。

三槽位分工

primary · utility_mm · fallback

主脑负责推理与工具调用，视觉槽专吃截图录屏，兜底槽在主链失败时接管 —— 三者独立配置，可以全是云端，也可以全在本地。

主脑 推理 · 工具调用 · 长上下文 （支持 reasoning 档位）
视觉 图片 / 音频 / 视频侧看 （qwen-vl · omni）
兜底 retry + fallback 链 主链异常时自动接管
Highlights

四个让它长在手边的功能

不只是个聊天窗口。它能主动找你、能被扩展、能自己按时跑，也能直接开口对话。

微信通道

integrations / weixin

人不在电脑前也能收结果、下指令。配对后长任务跑完直接推到微信，出门在外照样能催它干活。

  • 双向：推送结果，也接收你发来的新指令
  • 去重窗口：同一事件不会重复轰炸
  • 通道守卫：配对状态与投递失败可查
  • 与定时任务联动 —— channel_deliver 作为工作流最后一步

插件系统

extensions / 62 modules

把重复业务做成带界面的插件，钉在侧边栏常驻。脚手架生成、蓝图接入、校验、热重载一条龙。

  • 四种模板：CLI 桥接 · 多表 · React Flow · 基础页
  • 蓝图接入：给个 HTTP / 浏览器 / 上传场景就能生成
  • 热重载：改完即生效，UI 与运行时可分别重载
  • 登录态托管：认证面板 + 会话持久化，插件不必各自处理登录

定时任务

scheduler / APScheduler

跑通的流程固化成脚本，挂上 cron 就无人值守。巡检、报表、盯盘、备份，交给它按时做。

  • 两种触发：cron 循环 · 一次性定点
  • 两级调度：RPA 脚本任务与 Workflow 工作流分开管
  • CPU 动态限流：并发按机器负载自动收放
  • 需要人确认时会 park 住等你，不会闷头做错

实时语音模式

S2S Realtime · WebSocket

端到端语音直连，不是「录完再转文字」。说话中途想改主意，直接打断它，它当场停下听你的。

  • 真端到端：浏览器 PCM16 音频流 ↔ Omni 实时模型
  • Barge-in 打断：随时插话，立刻终止当前生成
  • 双路径：实时 E2E 与传统 TTS 通道，按能力自动选
  • 语音下也能出活：生成结果同步到可视化面板
